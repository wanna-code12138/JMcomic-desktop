## 3. 逐项门槛判定与架构决策

原报告依据计划 8 的门槛，对当时列出的模块作出以下决策：

1. **数据库写入协调器（进入 Task 2）**：
   - **决策**：**实施写入合并（Coalescing）与退出安全 Flush**；
   - **判定**：当时基线记录 `database.save` p95=4.6ms（≤8ms 门槛），因此暂不迁移 SQLite 或引入 sql.js Worker；数据规模或真实调用成本变化后需要重测。
   - **优化重点**：将连续高频的翻页页码、下载进度更新通过写入协调器防抖合并为 100ms~200ms 一次写入，退出应用时提供最大 2000ms 的等待保护。
2. **下载与缓存目录异步化（进入 Task 3）**：
   - **决策**：改造已识别的同步扫描入口，并评估结果缓存；不能仅凭存在异步辅助函数认定全部入口已完成改造。
   - **判定**：当时万级文件扫描记录超过 100ms，应将该路径改用异步 `fs/promises`；是否需要结果缓存及其失效规则，应按实际调用与测量决定。
3. **代理探测异步化（进入 Task 3）**：
   - **决策**：将代理探测中的 `execSync` 调用改为异步进程执行。
   - **判定**：同步等待外部进程会阻塞主线程，异步探测可移除这一等待；它不能证明其他窗口或主进程路径不再卡顿。

## 4. 历史复测记录与结论限制

原报告记录了 Task 2（写入协调器）与 Task 3（异步扫描与探测）的以下结果。2026-09-28 审计发现，协调器在性能候选中存在，但高频业务入口尚未使用 `scheduleDatabaseSave`；因此原报告不能证明业务写入合并已经生效。后续修复应以真实调用、落盘次数和退出恢复验证为准。

1. **持久化与数据库复测 (`database.flush`)**：
   - 协调器的设计目标是将翻页与下载进度更新合并为约 100ms 的批处理；接入情况必须从实际 IPC、下载和设置写入入口核对。
   - 原报告记载单次 export 耗时 p50=2.8ms、p95=4.5ms；未附该批原始样本，且 p95 不能证明每次完整落盘均小于 5ms。
   - `closeDatabase(2000)` 表达有限等待的设计；最后页码和任务状态是否可靠保存，需要覆盖真实退出、写入失败与恢复，不能由超时参数推断。
   - **当时决策**：暂不引入 sql.js Worker 或额外 SQLite 依赖；该选择基于记录中的规模和耗时，不等于主进程没有其他阻塞。
2. **目录扫描与代理探测复测**：
   - 下载已有页码检查（`existingPagesAsync`）与本地章节扫描（`resolveLocalChapterPagesAsync`）增加了异步读取路径；大目录下的遍历、排序和后续处理仍需测量。
   - 缓存维护与大小查询增加了异步 `fs/promises` 和 5 秒 TTL 缓存；总缓存清理与下载等其他入口需分别核对，不能据此宣称全部缓存 I/O 已异步化。
   - 代理探测将注册表查询改为异步进程执行（`execAsync`），减少同步等待；窗口交互是否改善仍需端到端测量。
   - **限制**：本文件没有覆盖当前版本的完整帧间隔、长时交互和事件循环延迟数据，不能宣称正常浏览中的 >100ms 卡顿已清零。
