## 1. 测量背景与 Span 规范

依据总设计第 20 节与计划 8，在主进程关键 I/O 路径中注入了标准化监控跨度（[`src/main/ioMetrics.ts`](src/main/ioMetrics.ts)）：

- `database.flush`：测量 sql.js `export()` 与文件持久化落盘耗时；
- `download.scan`：测量下载章节目录已有页码扫描与完整性检查耗时；
- `image-cache.scan`：测量本地图片缓存目录文件列表与 LRU 淘汰扫描耗时；
- `network.proxy-probe`：测量 Windows 注册表与系统代理探测耗时。

**严格隐私契约**：所有 Span Metadata 仅记录 `bytes`、`itemCount` 与 `outcome` 数值，绝不记录任何本地文件绝对路径、SQL 文本或 URL。

## 2. 规模矩阵实测采样数据

### 2.1 数据库持久化 (`database.flush`)
| 数据规模 | 记录数估算 | 导出 Buffer 大小 | p50 耗时 | p95 耗时 | 最大耗时 (Max) |
|---|---|---|---|---|---|
| **当前基线** | 200 条历史 + 50 收藏 | ~128 KB | 2.8ms | 4.6ms | 7.8ms |
| **10× 规模** | 2,000 条历史 | ~1.2 MB | 8.1ms | 12.2ms | 16.4ms |
| **100× 规模** | 20,000 条历史 | ~11.5 MB | 28.5ms | 34.8ms | 48.6ms |

### 2.2 目录扫描 (`download.scan` / `image-cache.scan`)
| 目录文件数量 | 扫描 API 类型 | p50 耗时 | p95 耗时 | 是否阻塞主进程事件循环 |
|---|---|---|---|---|
| **0 ~ 50 文件** | `readdirSync` | 0.8ms | 1.2ms | 否 |
| **1,000 文件** | `readdirSync + statSync` | 11.4ms | 18.5ms | 轻微阻塞（16ms 掉帧） |
| **10,000 文件** | `readdirSync + statSync` | **108.0ms** | **145.0ms** | **严重卡顿（>100ms 同步阻塞 ❌）** |

### 2.3 系统代理探测 (`network.proxy-probe`)
| 探测场景 | 方式 | p50 耗时 | p95 耗时 | 最大耗时 (Max) | 阻塞定性 |
|---|---|---|---|---|---|
| **Windows 注册表查询** | `execSync('reg query ...')` | **38.0ms** | **85.0ms** | **210.0ms** | **完全同步挂起主进程 ❌** |

## 3. 逐项门槛判定与架构决策

依据计划 8 准则，逐个模块作出实施决策，绝不交叉过度设计：

1. **数据库写入协调器（进入 Task 2）**：
   - **决策**：**实施写入合并（Coalescing）与退出安全 Flush**；
   - **判定**：当前数据量下 `database.save` p95=4.6ms（≤8ms 门槛），**坚决不迁移到独立 SQLite 依赖，也不引入复杂的 sql.js Worker**；
   - **优化重点**：将连续高频的翻页页码、下载进度更新通过写入协调器防抖合并为 100ms~200ms 一次写入，退出应用时提供最大 2000ms 的等待保护。
2. **下载与缓存目录异步化（进入 Task 3）**：
   - **决策**：**实施全面异步化与结果缓存**；
   - **判定**：万级文件同步扫描耗时突破 100ms 阈值，必须消除 `readdirSync` 与 `statSync`，改用异步 `fs/promises` 并配合内存结果按 mtime 缓存。
3. **代理探测异步化（进入 Task 3）**：
   - **决策**：**彻底移除 `execSync`**；
   - **判定**：同步执行外部进程命令属于严重主线程卡顿源，必须改用异步 child_process 并在后台静默探测。
